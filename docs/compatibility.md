# Minecraft Java 1.8.9 complete compatibility objective

The objective is a faithful source-method port of the supplied Java original into C/C++, with complete target-version compatibility. Matching directory names or independently recreating similar behavior does not satisfy that objective. Protocol 47 and the local MCP configuration identify the target version. C and, where appropriate, C++ and third-party libraries are permitted. The full objective stays active until each requirement below is implemented and tested against the target's actual behaviour.

Minecraft resources, MCP itself, decompiled source, mappings, JARs and private reference/test installations remain excluded from the public repository. User-provided licensed resources may be consumed locally without being redistributed. Public files contain translated C/C++ implementation, separately identified platform/dependency adapters, tests and documentation. The supplied Java originals remain private. Class/method port status is tracked in `docs/porting.md`; remaining native runtime dependencies are not claimed to be translated original classes.

## Completion requirements

1. Multiplayer: complete protocol-47 login/status/play packets, compression, authentication/encryption, session lifecycle, server list, LAN discovery, entity/world/inventory synchronization and failure handling. Both directions of interoperability must be exercised with actual 1.8.9 clients and servers, including online-mode where a legitimate account session is available.
2. Gameplay: Creative, Survival, Adventure and Spectator; complete block/item behaviour and metadata, player movement/collision, health/food/combat, inventories and containers, crafting/smelting/brewing/enchanting, entities/mobs/AI, drops, projectiles, explosions, redstone, tile entities, structures and the three dimensions.
3. World compatibility: dynamic streaming beyond a fixed demonstration area; 1.8.9 terrain/world generation parity, chunk lighting, time/weather/biomes, NBT, Anvil region storage, level/player data, save/reload and migration/error safety. Existing target-version saves must round-trip without silently losing supported data.
4. Client presentation: block/item/entity model and animation semantics, transparent/cutout/fluid shapes, texture/resource-pack loading, sounds, fonts/localization, chat and complete in-game screens/options/input. Resources must be loaded from authorized local sources, not bundled into the public repository.
5. Extension boundary: MCP 9.19 identifies the target Java version and protocol; it does not itself define a portable C mod ABI. Document extension interfaces as they become implemented. Arbitrary Java mod execution is a separate requirement and is not assumed from the request for Minecraft multiplayer compatibility. No such support may be claimed without a real, tested bridge/runtime.
6. Quality/delivery: preserve the supplied src structure, readable module boundaries, bounded untrusted parsing, reliable persistence, Windows and Linux verification where supported, independent review, public push under harnakam and an audited source-only public tree.

## Evidence ledger

The initial implementation proves a restricted offline creative session with nine materials and a 7x7-chunk dedicated world. This evidence is useful but does not satisfy full gameplay, save, resource or online-login compatibility.

The current implementation has 337 canonical item registry identities, including the original lit-furnace item at ID 62. The Creative palette has 336 visible item IDs because lit furnace has no Creative tab. The existing runtime preserves Slot/NBT, window-0 inventory/cursor state and click transactions, has a wired native inventory/creative-selection screen, and saves durable gzip player inventory files. Independent peers exercise full NBT, equipment, splitting, transfers, rejection locks, reconnects and aggregate size rejection. The actual local 1.8.9 game JAR successfully read a C-created player inventory and accepted the Java→C→Java Slot round-trip. This is progress toward requirement 2; it does not complete this objective.

The current inventory layer adds the valid player 2×2 recipe set (139 static recipes and dynamic NBT recipes), recipe consumption and remainder handling, and real item entities for drop/pickup/close. Transfer journals coordinate player/item file replacements and recover committed transfers before login. Both legacy Shift-crafting partial-output loss and the Creative full-inventory pickup sink are intentional target behaviours. These are separate from unintended persistence loss, which aborts before the commit point or recovers after it.

The workbench increment adds 365 regular static recipes, nine-input special recipes, a real 46-slot crafting-table lifecycle and native screen, durable inputs/remainders, and player/item/MapData journal commits. Missing maps resolve at spawn; empty maps create IDs; map scaling retains target NBT and the original Shift/number-key ID quirk. S34 reception and held-map pixels/markers are wired, and the dedicated server surveys supported loaded overworld terrain. A saved open table's inputs/cursor are released exactly once on reconnect after a crash.

The working tree now translates signed/reference ItemStack and NBT, InventoryPlayer, Slot/SlotCrafting, Container/Player/Workbench, all registered recipe bodies, inventory packet classes and selected play-handler methods. DataWatcher/S1C retain the original metadata references; selected client handlers use the source world and inventory fields. StatList/FurnaceRecipes construct craft statistics, and the StatisticsFile dirty/EntityPlayerMP statistics methods share the real counter map. Native player/world owners and storage encoders preserve managed references through all-owner transaction snapshots and reconstruct occurrences at wire/save boundaries. The running client/server now uses these canonical reference owners, source click prediction and source inventory handlers. Independent real TCP book-cloning tests reproduce the same input/entity remainder reference: another player's pickup changes the first player's grid to non-null count zero, commits both player files and the entity snapshot together, and survives restart without duplication. No separate value inventory, confirmation lock or client rollback owner remains. Complete Item/World/Entity dependencies, StatisticsFile JSON/S37/Scoreboard, client GUI/controller classes and the original server hierarchy remain open.

Open inventory work also includes all other external containers and their screens, complete creative variants/use behaviour, smelting/brewing/enchanting and item gameplay effects. Item physics still needs water flow, continuing fire/extinguishing, complete neighbour-dependent collision and audiovisual effects. Current item state is capped at 1024 entities and a 2 MiB snapshot. MapData is capped at 96 entries; original short map-counter wrap and ItemStack damage clamps are retained; terrain surveying is restricted to supported loaded overworld terrain. The ported MapInfo follows original initial-full, dirty-rectangle and icons-only scheduling. ItemFrame tracking, full world dependencies and complete source-class coverage remain open. Rendering still uses original procedural cube materials and symbolic item geometry. These limits and missing behaviours remain part of the full objective.

Unimplemented or unverified requirements remain open. Tests cover their named contracts, not all of Minecraft by implication.

Source inventory ticks now call the original main-array traversal and ItemStack decrement/virtual dispatch order in both live client and server. The original base Item.onUpdate is empty; ItemMap is the original registry's sole override. Duplicate stack references update once per occupied slot, signed counts do not filter updates, and a NULL Item fails after a positive animation decrement. The original GuiIngame hotbar method drives native body transforms before fixed overlays; callback expression order and the retained local stack match independent target-JAR records. Complete player/World ticks, resource models/textures, RenderItem/FontRenderer and the remaining GUI remain open.

The entire Timer constructor, updateTimer and ten source fields are now translated. The live client owns a traced Timer in its canonical graph, updates it once before network execution and passes only signed elapsedTicks and the exact renderPartialTicks field through later graph adoption. Source clock ordering, drift correction, first-update behavior, signed wrap, float rounding and excess-whole-tick discard are retained. Native millisecond and high-resolution clock callbacks replace the two platform clock dependencies. One-shot input, player physics, the complete Minecraft game loop and integrated-singleplayer pause remain native or unfinished; this Timer port does not establish full tick parity.

The Random scalar dependency now follows the Java 8 API, with separately traced World, player and item Random references and one lazy external process Math.random stream. Native owner factories reproduce the named inherited initialization draws, not the complete original constructors. MathHelper.getRandomUuid and Entity's UUID NBT segment retain source draw, mask, getter and assignment order. Player loading restores the required profile UUID reference before Inventory. UUID segments do not serialize Random state or consume draws; full EntityPlayer NBT, including XpSeed's conditional nextInt, remains unported. Native spawn decoding preserves signed pitch/yaw and applies packet velocity only for positive data. The original isSilent byte==1 predicate now controls pickup sound and its item-Random draws. Gaussian, full JDK Random/UUID classes and JDK concurrency semantics remain open; transaction snapshots retain native owner streams while external process draws are not rolled back.

Source action/manager subsets are connected: SP close/drop/stat, controller held/creative/air use, server ItemStack/ItemInWorldManager map use and direct map/player tracking. `--gamemode 0` selects nonCreative inventory/pickup/use branches for verification; it is not a complete Survival mode. Native scalar entity motion, packet adapters for unported classes, terrain, GUI and full block interaction remain explicit boundaries. Statistics counters are managed source state, while JSON persistence, full scoreboard classes and achievement announcements remain incomplete. Server saved-file/inventory caps and the client graph allocation cap are native policies rather than original game semantics.
