# C919 native multiplayer design

Target: Minecraft Java Edition 1.8.9, wire protocol 47, as identified by the local MCP configuration. The supplied MCP Java original is the private source of the class/method translation. No MCP source, binary, mappings, Minecraft assets, or runtime data are distributable inputs.

The objective is complete target-version compatibility as tracked in `docs/compatibility.md`. The initial original C11 creative voxel client and dedicated server are an incomplete starting point. C++ and libraries may be used where necessary. The supplied `src/minecraft/net/minecraft` hierarchy is the destination for original classes. Named class methods are being ported and wired into the existing runtime; the runtime is not itself a completed source port. `docs/porting.md` identifies translated methods and dependency adapters. Existing module boundaries include: network framing and codecs, shared world and storage, authoritative server, and native client rendering/input.

The server accepts protocol-47 status/login/play sessions, sends independently generated terrain, maintains players, and synchronizes movement, chat, inventory, dropped items and validated block edits. Offline identities are explicitly local/LAN identities. The client negotiates framing/compression, receives actual server chunks, entities and inventories, renders procedural original block materials, and sends gameplay actions. World persistence uses a validated C919 format; player inventory and item-entity persistence use gzip NBT and target-version resource-name item IDs. Anvil world saves and Java mod execution are not supported.

NBT and Slot ownership is shared by both ends. Inventory operations produce their actual transaction return value and any dropped stack; transport, permissions, world effects and persistence remain caller responsibilities. The server commits durable accepted inventory changes before confirmation. Legitimate return-value mismatches trigger a lock and authoritative resynchronization. The client holds further clicks until a rejection's slots and cursor have both arrived, regardless of fragmentation or order. It does not overwrite an external server's hotbar during login.

The crafting module derives player-window slot 0 from the 2×2 inputs, consumes recipes through the same click/transaction path, and returns owned drop effects. Closing the player inventory drops its cursor and remaining inputs, then clears the derived result. Original static recipe definitions and dynamic NBT recipes are shared by client prediction and the authoritative server. The legacy target's Creative full-inventory pickup sink and partially fitting Shift-craft behavior are intentional compatibility rules.

The item-entity module owns complete Slot NBT, physics, pickup and merge rules, packet encoding and persistent snapshots. The server ticks items at 20 Hz, tracks each item per peer only after its chunk has been sent, and synchronizes spawn, velocity, metadata, movement, collection and destruction. The native client keeps server fixed-point coordinates separately from local simulation so relative movement does not accumulate prediction drift. Entity counts and aggregate metadata are bounded. Water flow, continuous burning and complete neighbor-dependent collision behavior remain open compatibility work.

An inventory/world-item/MapData transfer updates up to three files. The server first writes validated pending player, item and MapData snapshots, then atomically writes a manifest containing their sizes, checksums and canonical player UUID. The durable manifest is the commit point. Recovery validates every staged snapshot before checkpointing any destination and removes the manifest only after all checkpoints succeed. Version-1 two-file manifests still recover without touching map storage. A failure before commitment preserves the old in-memory state; a failure after commitment retains the new state, stops the server and leaves recovery evidence intact. Startup completes recovery before loading items or admitting players. Item-only checkpoints use the same journal. Periodic physics snapshots are separate from immediate durable inventory transfers.

Wire parsers bound lengths and reject invalid data. Slow clients have bounded queues. Invalid coordinates, non-finite movement, out-of-range edits, malformed handshakes, and duplicate names are rejected. The server defaults to loopback. Online-mode session authentication and encrypted login are not supported; the client must report this clearly instead of pretending to connect.

Verification includes C tests for codecs, world boundaries/persistence, NBT inventories, crafting, item entities and transfer recovery; independent Python TCP tests for multiplayer, client parsing, transactions, crafting, drops, pickup and failed-checkpoint restart; Windows and Linux strict builds; and staged-blob public index audits. Local original-game fixtures compare specific recipe, item and container contracts, while native framebuffer fixtures check the rendered layout. Vanilla GUI interoperability is only claimed if actually exercised.

The first named source ports are InventoryCrafting, InventoryCraftResult, C08PacketPlayerBlockPlacement and selected MapData/ItemMap methods. Crafting decrements and remainder placements invoke the original inventory notification points instead of only one final recomputation. C08 construction/read/write/getters and handler dispatch run on both network ends. MapInfo owns per-viewer counters and dirty rectangles; transactional map copies retain this transient state even when no persistent NBT changes. InventoryPlayer main order is adapted to the protocol-window storage order at the server boundary. Rendering, resource access, socket I/O and durable journaling are native dependency adapters.
